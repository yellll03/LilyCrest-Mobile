Executive Verdict

One audit pass across five parallel workstreams (auth/session/navigation, home/notifications/announcements, billing/payment, maintenance/documents/profile/password, and API-contract/dead-code/build-config) found a single High-severity issue — a real tenant-only boundary gap — and a handful of Medium/Low items. The High finding, plus two of the Medium findings, have been fixed and verified in this pass (backend + frontend test suites green, 0 lint errors). No reservation, applicant, or admin workflow is reachable from the tenant app. Remaining items are genuinely non-blocking: an Android permissions review, a payment-status UX nuance, and a maintenance-ticket idempotency hardening — none of which risk tenant data, money, or cross-account exposure.

H

Security Findings

HighMobile login endpoint authenticated admin accounts with no role check downstream

Locationbackend/controllers/auth.controller.js:364, backend/middleware/auth.js, frontend/src/context/AuthContext.js

Scenario/auth/login and /auth/google intentionally still authenticate admin accounts (the web admin panel shares them), but neither authMiddleware nor the frontend's session logic checked role afterward. An admin session could reach every tenant-scoped screen and endpoint in the mobile app.

FixFixed — new tenantMiddleware rejects admin/superadmin on every tenant router (backend), and AuthContext now rejects non-tenant roles at every point the app marks itself authenticated: login, OTP verify, Google sign-in, session hydration, and checkAuth (frontend). Verified with the full backend (304) and frontend (194) test suites, both green.

Verified soundIDOR — no cross-tenant reads or mutations found

Billing, payment, maintenance, documents, and notifications all resolve ownership from req.user, never a client-supplied ID. Cross-tenant billingId/requestId/notificationId lookups return 404, not another tenant's record.

Verified soundBranch isolation is backend-authoritative

Announcement visibility is derived from the tenant's own occupancy record server-side (resolveTenantBranch), never trusted from the client, and defaults to hidden rather than visible when branch can't be resolved.

MediumBroad Android permissions warrant a pre-submission review

Locationfrontend/android/app/src/main/AndroidManifest.xml:3-9

SYSTEM_ALERT_WINDOW (draw-over-other-apps) plus legacy READ/WRITE_EXTERNAL_STORAGE are declared. These are Play Store review flags and, if unused, unnecessary attack surface.

FixDeferred — confirm which native module needs SYSTEM_ALERT_WINDOW before stripping it; not changed blind in this pass.

Verified soundBuild/secrets hygiene

Production API host is https://api.lilycrest.space across all 4 EAS build profiles, with a runtime guard that hard-fails on a localhost/private-IP host. Cleartext traffic is disabled app-wide. google-services.json and .env are gitignored and confirmed untracked.

I

Authentication / Session Findings

  • Login (email/password, Google, OTP): empty/malformed input, duplicate-tap, and offline/timeout are all handled with clear, tenant-safe messaging; non-tenant roles are now rejected client-side in addition to the pre-existing backend rejection at /auth/login//auth/google for genuinely unregistered accounts.
  • Session restoration: hydration always terminates in a definite authStatus — no path leaves the app stuck on a loading screen. A stale AsyncStorage cache used to be able to outlive a backend-side deactivation until the next successful poll; treating 403 the same as 401 during hydration (part of this pass's fix) closes that window too.
  • Logout: local state (user, notifications, badge count) clears synchronously before best-effort server teardown, SecureStore/biometric credential clearing, and push-token disable. Back-navigation after logout cannot reopen protected screens — the root-layout guard re-evaluates on every route change.
  • Debug route: frontend/app/debug/api-health.jsx self-gates on __DEV__ independent of how it's entered, with a regression test locking the behavior in.
J

Billing / Payment Findings

Financial source-of-truth is backend-only throughout: rent, utilities, penalties, credits, previous balance, and outstanding amount are all computed server-side and only formatted (never recomputed) on the client. The payment path resolves amount and ownership from the authenticated tenant's own bill record — a tenant cannot pay another tenant's bill by manipulating an ID. Webhook signature verification fails closed when unset, HMAC comparison uses a timing-safe check, and bill-paid writes are atomic and idempotent against duplicate webhook delivery. Checkout-session creation has both a 20-minute reuse window and a 20-second claim lock, so double-tap or retry storms cannot mint two live PayMongo sessions.

LowA declined/failed payment looks identical to a merely-slow one

Locationfrontend/app/payment-success.jsx

The success screen polls for up to 60s and then shows a generic "still processing" message on timeout — the same message a genuinely failed payment would produce, even though PayMongo already emits a distinct payment.failed webhook event.

FixDeferred — needs the failed-state to be surfaced through getCheckoutStatus and branched on in the UI; not changed in this pass.

Low / MaintainabilityDual bill-collection reconciliation is defensively written but structurally complex

Bills live in two parallel collections (legacy billing and current bills), reconciled by a scoring heuristic. Current behavior is confidence-ordered correctly (paid status dominates), but the branch count is a real long-term audit-surface cost. Recommend eventual migration to a single collection — no immediate action required.

K

Maintenance Findings

Every tenant-facing maintenance lookup filters by user_id matching the authenticated session — cross-tenant reads return 404, not the record. Status labels are single-sourced between backend (friendlyStatusCopy) and frontend, so "In Progress" never disagrees with itself across screens. Provider assignment is admin-only (PATCH /maintenance/admin/:id/status, gated by adminMiddleware) with no corresponding call site anywhere in the tenant app — the tenant only ever sees a read-only "a service provider has been assigned" line. The two open items are the description max-length guard and submission idempotency key covered in §G.

L

Notification / Announcement Findings

Notifications have one source of truth (AuthContext) — the codebase's own comments confirm this was consolidated from three separate implementations in a prior pass. Mark-read is optimistic with rollback on failure, ownership-checked server-side, and polling correctly stops on logout (state reset happens synchronously, ahead of the interval-clearing effect). Announcement branch visibility is a single backend implementation reused by the notification feed, so the two can't disagree — a tenant from branch A cannot see branch B's restricted announcement, and unresolvable branch defaults to hidden, not visible.

M

Document / Contract Findings

Tenant documents are resolved from a fixed template registry personalized only with the requesting tenant's own data — there's no guessable per-user document ID to exploit. Contracts are proxied server-to-server to a separate Capstone-Website service; the bearer token is forwarded byte-for-byte and re-validated upstream, so ownership enforcement for contract data lives in that external repo and wasn't independently verifiable from this codebase (flagged as an out-of-scope dependency, not a confirmed gap). No lingering applicant/reservation terminology was found in contract or document UI, and no admin-only generate/edit controls exist client-side.

N

Profile Findings

Editable fields match backend support exactly — name, email, and address are read-only client-side with matching backend rejection messages; only username, phone, and photo are live, with identical validation rules on both sides. A grep for applicant-oriented status strings ("Pending Move-in", "Application Pending", "Reservation Approved") found no live matches — the only hits are in a regression test that explicitly asserts this text stays absent, confirming a prior fix rather than an open issue.

R

Deferred Recommendations

Genuinely non-blocking — none of these risk tenant data, money, or role boundaries as shipped:

  • Add a short-lived idempotency key to maintenance ticket submission to prevent duplicate tickets on network-retry.
  • Add a frontend max-length guard (1000 chars) on the maintenance description field, mirroring the backend cap.
  • Surface PayMongo's payment.failed event through getCheckoutStatus so a declined card shows a distinct message from a slow-but-pending one.
  • Review whether SYSTEM_ALERT_WINDOW and legacy storage permissions in the Android manifest are actually used before Play Store submission; strip if not.
  • Remove the four dead admin-only functions bound into frontend/src/services/api.js (unreachable, but unnecessary bundle surface).
  • Chat/chatbot routes (chat.routes.js, chatbot.routes.js) were not included in the tenant-only middleware pass — no audit flagged them, but they weren't independently re-verified either. Worth a follow-up pass before treating the role-boundary fix as fully exhaustive.
  • Plan an eventual migration off the dual legacy/current bill-collection reconciliation — currently safe but structurally complex.
