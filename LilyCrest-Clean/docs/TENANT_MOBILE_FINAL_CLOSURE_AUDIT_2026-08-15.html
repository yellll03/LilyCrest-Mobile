Chat / Chatbot Security Results

ClosedTenant-only middleware applied to every tenant-facing chat/chatbot route

chat.routes.jstenantMiddleware added to /start, /me, /:conversationId/messages (GET+POST), /:conversationId/close. Admin sub-routes (/admin/*) stay adminMiddleware-only, untouched.

chatbot.routes.jstenantMiddleware added to /message, /request-admin, /reset, /live-status/:sessionId, /history. Deliberate exception: /close-live-chat was left authMiddleware-only because its controller has legitimate owner-OR-admin semantics (an admin can also close a live chat they're handling) and no separate admin-only route exists to move that case to — adding tenantMiddleware there would have broken real admin functionality. This is documented inline in the route file.

Verified soundOwnership was already correctly enforced inside both controllers

chat.controller.js's buildTenantConversationFilter(req.user) scopes every tenant lookup; a conversation ID belonging to another tenant returns 404 (CONVERSATION_NOT_FOUND), not the record. chatbot.controller.js's getOwnedLiveChat(sessionId, userId) and an identity-fingerprint check (resets session history if a session_id is reused by a different identity) already existed — code comments indicate this was hardened in an earlier pass, before this audit.

Test scenarios (backend/tests/chatTenantBoundary.test.js — 9 tests, all passing)

  • Tenant A → own conversation = allowed (200)
  • Tenant A → Tenant B's conversation, read or reply = rejected (404, project's standard IDOR convention)
  • Admin / superadmin role → any tenant chat or chatbot route = rejected (403 via tenantMiddleware, tested for both roles and case variants)
  • Malformed conversation ID = safe 404, not a crash
  • Route-level middleware presence verified by introspecting the Express route stack directly (not just behavior), so a future refactor that silently drops the middleware would fail this test even if ownership checks still happened to work

State cleanup

No persistence layer stores chat messages (useAssistantChat.js: "No persistence: always start fresh"). The chatbot session ID is useMemo'd on user?.user_id in LilyAssistantScreen.jsx, so it regenerates on account switch; the message list is local component state that resets on remount. Confirmed no Tenant-A chat content can appear after a Tenant-B login.

F

Maintenance Results

ClosedSubmission idempotency implemented, including the true concurrency race

Frontend mints a UUID (client_request_id) once per submission attempt (expo-crypto's randomUUID()), held in a ref that survives retries and clears only on success/discard. Backend: fast-path lookup returns the original ticket on a sequential retry (200, not a new 201); a unique sparse index on {user_id, client_request_id} (server.js) makes the near-simultaneous race safe — the losing insert hits a duplicate-key error (code 11000), caught and resolved to the winner's ticket rather than a 500 or a silent second ticket. Requests without a key (older app builds) are unaffected.

Tests (backend/tests/maintenanceIdempotency.test.js — 11 tests, all passing)

  • Sequential retry with the same key → one ticket, second call returns 200 with the original request_id
  • Promise.all simultaneous duplicate submit → exactly one document created; responses are [200, 201], never two 201s
  • Different key → distinct ticket (no false-positive dedup)
  • No key sent → still works (backward compatible)
  • Malformed key (path-traversal-shaped string) → treated as absent, never trusted verbatim into the document
  • Description length: blank, whitespace-only, 9 chars (below min), exactly 10 (min, accepted), exactly 1000 (max, accepted), 1001 (rejected) — all pass

Frontend: MAX_DESCRIPTION_LENGTH = 1000 mirrors the backend constant with a code comment cross-referencing it; a live "742 / 1000" counter renders below the field, turns red past the limit, and the TextInput has a hard maxLength so typing past 1000 is physically prevented (backend remains authoritative regardless). Status mapping and the tenant/provider boundary were re-verified unchanged from the prior audit: friendlyStatusCopy (backend) and the frontend label mapper agree on every value, and no admin-only provider-assignment call site exists client-side.

ClosedPaid / pending / failed / cancelled are now distinguishable, backend-normalized

getCheckoutStatus now returns a normalized status enum (normalizeCheckoutStatusForClient) collapsing raw PayMongo payment_intent/session strings into paid | pending | failed | cancelled | unknown, plus a raw_status field kept for diagnostics only. payment-success.jsx now branches on this: paid shows the existing green success state; failed stops polling immediately and shows a red "Payment Failed... please try again" state with a Try Again button routed back to /payment; cancelled stops polling and shows a distinct grey "Payment Cancelled" state; pending keeps the existing amber "still verifying" copy and 60s polling behavior. No path implies success before the backend confirms it.

Tests (backend/tests/paymongoStatusNormalization.test.js — 6 tests, all passing)

  • paymentConfirmed: true always → "paid", regardless of raw status text underneath it
  • failed/declined → "failed"; cancelled/voided/expired session → "cancelled"
  • pending/awaiting_payment_method/awaiting_next_action/processing/bare active session → "pending"
  • Unrecognized combination → "unknown" (never a false paid/failed)

READ_EXTERNAL_STORAGE / WRITE_EXTERNAL_STORAGENoLegacy pre-scoped-storage permissions; the app's attachment/document flows already use expo-image-picker/expo-document-picker's scoped pickers. Same blob-util README origin as aboveRemoved + suppressed

Fix detail

Because react-native-blob-util's own native manifest still declares these three permissions unconditionally, deleting the <uses-permission> lines from the checked-in AndroidManifest.xml alone would not survive Gradle's manifest merge on the next build. Explicit tools:node="remove" overrides were added for all three, which is the correct mechanism to suppress a permission a dependency re-injects.

Not build-verified — this environment has no Android SDK/Gradle toolchain to produce a merged manifest and confirm the override actually takes effect. The fix is applied and evidence-backed, but should be confirmed against a real build's merged_manifest output before Play Store submission, per the instruction not to mark something verified when it was only inferred.
